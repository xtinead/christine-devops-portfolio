Reproducible infrastructure and recovery

Rebuildable by Design: What the Clixx GitOps Platform Taught Me About Reproducible Infrastructure

Why a platform is not truly reproducible until another engineer can deploy it, validate it, tear down disposable components safely, and rebuild it without undocumented knowledge.

September 26, 2026 · 9 min read · Christine Adelusi

Cloud infrastructure is not truly reproducible because a deployment succeeds once. It is reproducible when another engineer can follow the documented process, create the same platform, validate it, tear down the disposable parts safely, and rebuild them without relying on undocumented knowledge.

That principle shaped the Clixx GitOps Platform, a production-style AWS and Kubernetes project built with Terraform, Jenkins, Amazon EKS, Amazon ECR, and Argo CD. The platform was designed not only to deploy a WordPress application, but also to make ownership, recovery, change control, and reconstruction explicit.

Workplace value: the ability to rebuild a platform is evidence that the architecture is understood, the automation is complete, and operational knowledge is not trapped with one engineer.

Reproducibility is an operational requirement

Infrastructure as Code is an important part of reproducibility, but Terraform files alone do not guarantee a reliable rebuild. A platform can still depend on manually created resources, unclear state ownership, local secrets, undocumented deployment steps, direct kubectl changes, hidden dependencies, or teardown procedures that fail when cloud resources retain attachments.

For Clixx, I treated teardown and rebuild as lifecycle operations rather than emergency procedures. The goal was to make the path from an empty environment to a validated application understandable and repeatable.

Designing clear ownership boundaries

Terraform owns the AWS and Kubernetes infrastructure. Jenkins validates changes, creates reviewed Terraform plans, builds immutable application images, and publishes them to Amazon ECR. Git stores desired application state. Argo CD reconciles that state into Amazon EKS.

This separation prevents the CI server from becoming an all-powerful deployment host. Jenkins does not need direct production kubectl access. An application release becomes a Git change that can be reviewed, audited, reverted, and reconciled by Argo CD.

The platform is also separated into lifecycle layers:

  1. Bootstrap: protected remote Terraform state using Amazon S3 and DynamoDB.
  2. Platform infrastructure: networking, EKS, IAM integrations, RDS, EFS, ingress dependencies, and supporting AWS services.
  3. GitOps: Argo CD installation and the connection between the cluster and declared application state.

These boundaries reduce blast radius and clarify which layer must exist before another can be created or destroyed.

Protecting state while rebuilding infrastructure

Rebuildability does not mean deleting everything indiscriminately. Clixx contains relational data in Amazon RDS and uploaded application content on Amazon EFS. Those resources require a different lifecycle from replaceable compute resources such as Kubernetes nodes, controllers, and pods.

The teardown design distinguishes disposable infrastructure from protected data. Backup, snapshot, retention, and restore decisions are made before destructive operations begin. Terraform state is stored remotely and locked to prevent concurrent changes, while environment configuration is versioned without storing credentials in Git.

Recovery principle: a rebuild process is only useful when it restores the service without creating an avoidable data-loss event.

Making the pipeline repeatable for the team

A team-ready workflow needs guardrails and evidence, not merely a collection of commands. The Clixx workflow uses Terraform validation and saved plans so the reviewed plan is the artifact applied after approval. Jenkins assumes AWS roles with temporary credentials, and environment and layer parameters make the execution target explicit.

After rebuilding, validation checks cluster readiness, Argo CD reconciliation, application health, ingress routing, persistent storage, database connectivity, autoscaling resources, and monitoring signals.

Another engineer should be able to answer:

  • What am I changing, and which environment and layer am I targeting?
  • What state and data are protected?
  • What evidence should I review before approval?
  • How do I confirm that the rebuild succeeded?
  • How do I roll back or investigate a failure?

If those answers exist only in one person’s memory, the platform is not operationally mature.

What teardown testing reveals

Building is usually the easiest path through a cloud platform. Teardown exposes hidden ownership problems. Resources may remain because a repository is not empty, a network interface is attached, a security group is referenced, a controller has not completed cleanup, or a resource was created outside the expected state.

These are not just cleanup inconveniences. They reveal gaps in dependency management, ownership, sequencing, and verification. Testing teardown taught me to use prechecks, explicit safeguards, bounded cleanup logic, and post-destroy verification. A successful command is not enough; the process must confirm that intended resources are gone while unrelated account infrastructure remains untouched.

How this applies in a work environment

Reproducibility shortens onboarding because new engineers can follow documented workflows instead of reverse-engineering the platform. It improves review because saved plans and Git history show what will change. It reduces key-person risk by moving operational knowledge into version-controlled automation and runbooks. It also improves environment consistency because development, staging, and production share an architecture with controlled configuration differences.

During an incident, a team that knows how infrastructure is created, where state is stored, which data is protected, and how health is validated can treat recovery as a practiced workflow rather than an improvised series of console actions.

Skills demonstrated through the Clixx platform

  • Layered AWS and Kubernetes architecture design
  • Reusable Terraform workflows with protected remote state
  • IAM roles, OIDC integration, and temporary credentials
  • Separation of CI responsibilities from GitOps delivery
  • Persistent-data protection and disaster-recovery planning
  • Dependency, lifecycle, and state-management troubleshooting
  • Approval, rollback, validation, and teardown guardrails
  • Documentation that enables other engineers to operate the platform

Final lesson

A platform is not finished when it can be deployed. It is operationally mature when it can be changed, validated, recovered, and rebuilt through a process the team understands.

The Clixx GitOps Platform moved my thinking beyond infrastructure as a collection of resources. I now treat it as a lifecycle: provision, validate, operate, change, recover, destroy, and rebuild. That lifecycle mindset is central to how I approach Senior DevOps and Platform Engineering work.
