GitOps and continuous delivery

Why Jenkins Should Not Deploy Directly to Production Kubernetes

How I reduced the blast radius of CI credentials by separating Jenkins orchestration from Argo CD runtime reconciliation in my Clixx GitOps platform.

March 24, 2025 · 10 min read · Christine Adelusi

The platform context

I built the Clixx GitOps Platform as a production-style AWS and Kubernetes environment. The objective was not simply to deploy an application to Amazon EKS. I wanted to show how infrastructure provisioning, CI governance, and runtime delivery could work together as a safe, auditable, and repeatable platform.

Terraform provisions the VPC, EKS cluster, IAM resources, ALB infrastructure, EFS, and RDS where required. Jenkins coordinates validation, infrastructure workflows, and image creation. Argo CD continuously reconciles Kubernetes resources from Git.

The direct-deployment anti-pattern

A common implementation gives Jenkins a kubeconfig or service-account token and lets the pipeline run kubectl apply against production. It appears efficient, but it also turns the CI server into a privileged production operator.

A compromised agent, plugin, credential, or pipeline could then affect the cluster. Deployment history becomes tied to pipeline logs, manual cluster changes may remain unnoticed, and rollback becomes another imperative command rather than a reviewed desired-state change.

The key risk: when CI can both produce an artifact and directly change production, one credential boundary spans too much of the delivery system.

The responsibility boundary I implemented

  1. Terraform manages platform infrastructure. CI validates plans, and an approval gate is required before apply.
  2. Jenkins manages continuous integration. It validates source, builds an immutable image, publishes it to Amazon ECR, and updates the desired version through Git.
  3. Argo CD manages runtime reconciliation. It pulls approved Kubernetes configuration and aligns Amazon EKS with that declared state.

Jenkins does not require Kubernetes API credentials to complete its job. Argo CD does not build application source. Git is the contract between the two systems.

The resulting delivery flow

  1. A change is proposed and reviewed in Git.
  2. Jenkins validates the code and relevant Terraform configuration.
  3. Infrastructure changes stop at manual approval before apply.
  4. Jenkins builds and publishes the immutable image to ECR.
  5. The desired image version is updated in the GitOps configuration.
  6. Argo CD detects the change and reconciles EKS.
  7. Kubernetes reports workload health while Argo CD reports synchronization state.

Security and governance benefits

Reduced credential blast radius

Jenkins receives permissions for its CI and approved AWS responsibilities, but not direct Kubernetes API access. This limits what a compromised or misconfigured pipeline can change.

A Git-based audit trail

The GitOps repository records the version and configuration that should be running. Changes are reviewable through commits and pull requests instead of existing only as executed pipeline steps.

Approval at the high-risk boundary

Manual approval before Terraform apply places human review where an infrastructure change could alter the platform or expand its blast radius. The goal is controlled automation, not manual operation.

Drift detection and rollback

If a managed Kubernetes resource is changed outside the approved workflow, the cluster no longer matches Git. Argo CD detects the divergence and can reconcile the resource back to declared state.

Rollback uses the same controlled mechanism. I revert the Git change that introduced the unwanted state, and Argo CD reconciles the cluster to the earlier version.

Operational principle: rollback should use the same governed path as deployment. A Git revert preserves reviewability and avoids undocumented emergency state.

Engineering challenges and lessons learned

Safe GitOps delivery also depends on reproducible infrastructure. I isolated the S3 state store and DynamoDB locking resources in a permanent Terraform bootstrap layer so a platform teardown cannot remove the state required for rebuilding. The remaining infrastructure can be destroyed and recreated from code.

The central lesson is that CI/CD design is a security architecture decision. Jenkins is effective at validation, orchestration, and artifact creation. Argo CD is effective at comparing declared Kubernetes state with running state. Giving each tool a narrow responsibility created a platform that is easier to audit, recover, and explain.

This is the pattern I would carry into production engineering: keep privileges narrow, make desired state visible, require approval for high-impact changes, and design rollback and rebuild paths before they are needed.
