Observability and scaling

Building Observability and Autoscaling into Kubernetes from the Start

How I combined Kubernetes-native metrics, AWS infrastructure monitoring, actionable alerting, and load-tested HPA behavior in an EKS operations platform.

Deployment is not the finish line

When I began this project, I wanted to focus on what happens after a workload reaches Kubernetes. A successful deployment proves that resources were accepted and containers started. It does not prove that the application is healthy under load, that operators can diagnose a failure, or that scaling will behave as expected.

I built the Kubernetes Observability and Scaling Platform to complement my infrastructure and GitOps work. The repository concentrates on the operational side of Amazon EKS: collecting metrics, visualizing workload behavior, monitoring AWS infrastructure, defining useful alerts, and examining how Horizontal Pod Autoscaler responds to demand.

Core principle: observability and autoscaling are platform capabilities that must be designed and validated—not features to add after deployment.

The layered observability architecture

I intentionally used both Kubernetes-native and AWS-native monitoring because neither layer provides the complete runtime picture on its own.

  • Prometheus is the primary in-cluster metrics system. It collects time-series data from workloads, cluster components, and application endpoints that expose metrics.
  • Grafana turns those metrics into dashboards for workload health, resource utilization, application trends, cluster behavior, and scaling analysis.
  • CloudWatch provides infrastructure metrics, logs, events, alarms, and visibility into the AWS resources supporting the EKS platform.
  • HPA converts measured workload demand into controlled changes in pod replica count.

This separation matters during diagnosis. An unhealthy pod may be caused by the application, resource pressure, a cluster component, or an underlying AWS condition. Prometheus and Grafana expose what is happening inside Kubernetes; CloudWatch adds the infrastructure context surrounding it.

Metrics, dashboards, and alerts serve different purposes

I treated metrics, dashboards, and alerts as related but distinct operational tools.

Metrics preserve evidence

Prometheus stores time-series signals such as CPU usage, memory usage, pod health, request throughput, error rates, and workload behavior. Historical data makes it possible to compare current symptoms with earlier platform behavior instead of relying only on the present state.

Dashboards support investigation

Grafana provides the visual context needed to identify trends, correlate resource use with application activity, examine scaling events, and investigate bottlenecks. A dashboard helps an operator ask better questions; it does not decide which conditions deserve an interruption.

Alerts demand action

The alerting strategy uses AWS-native alarms and operational thresholds to surface conditions tied to real risk. I documented that alerts should be actionable, useful during incident response, and limited enough to avoid noise.

Alerting lesson: if an operator cannot explain what action an alert should trigger, the threshold or the alert itself needs more design work.

Designing HPA as operational behavior

Horizontal Pod Autoscaler evaluates workload signals such as CPU utilization, memory usage where configured, and sustained application demand. When a threshold is exceeded, Kubernetes increases the number of replicas; after demand falls, it can reduce them again.

The YAML object is only the starting point. Meaningful autoscaling requires deliberate choices for minimum replicas, maximum replicas, thresholds, and stabilization behavior. Resource requests also matter because utilization-based scaling depends on an appropriate baseline.

I therefore viewed HPA as a feedback loop:

  1. The workload receives increasing demand.
  2. Resource consumption changes.
  3. The metrics pipeline makes that change available.
  4. HPA evaluates actual values against the target.
  5. Kubernetes changes the desired replica count.
  6. New pods start and become ready.
  7. Operators observe whether availability and resource behavior improve.

Validating scaling under load

One of the strongest lessons from this project was that an HPA configuration should not be considered complete merely because it exists. I documented load simulation as the mechanism for checking whether runtime behavior matches the design.

During a scaling validation, I want to observe:

  • the demand level that triggers scale-out;
  • how long it takes metrics and HPA to react;
  • whether additional replicas become ready;
  • resource utilization during the transition;
  • whether the workload remains available;
  • how long stabilization takes after demand falls; and
  • whether replicas eventually scale back in without oscillation.

This closes an important gap between configuration and evidence. A threshold that looks reasonable in a manifest may react too slowly, scale too aggressively, or produce unstable behavior when tested.

How the design supports incident response

I used a short set of operational questions to evaluate whether the monitoring model was useful:

  • Are the workloads healthy?
  • Are pods under resource pressure?
  • Is scaling occurring?
  • Are infrastructure alarms firing?
  • What changed recently?

Grafana supports workload and cluster investigation. Prometheus supplies metric history. CloudWatch provides infrastructure alarms and AWS context. Together, these tools reduce the time spent proving where a problem is not and help narrow the next troubleshooting action.

The architecture also reinforces the value of connecting observability with delivery information. Metrics show symptoms, while recent GitOps or infrastructure changes provide context about what may have introduced them.

Lessons learned

Observability must be designed

Adding a dashboard at the end of a project does not guarantee useful visibility. The platform and workload must expose signals that correspond to health, capacity, and operational risk.

Workload and infrastructure monitoring are complementary

Prometheus and Grafana explain behavior inside Kubernetes, while CloudWatch explains conditions in the AWS environment supporting it. Reliable diagnosis needs both perspectives.

Autoscaling is not the same as capacity planning

HPA can add pods only within configured boundaries and available cluster capacity. Maximum replicas, node capacity, requests, limits, readiness, and external dependencies still constrain the system.

Scaling should be observable and testable

An operator should be able to see why the replica count changed, whether the response helped, and when the platform returned to a stable state. Load testing provides the evidence that the control loop behaves as intended.

This project changed how I define a complete Kubernetes platform. Deployment makes a workload available. Observability makes its behavior understandable. Alerting makes risk actionable. Tested autoscaling allows the platform to respond to demand with controlled, visible behavior.
